# เว็บแอปพลิเคชันสำหรับประเมินและแนะนำการปรับปรุงเว็บไซต์เพื่อผู้พิการตามมาตรฐาน WCAG เบื้องต้น

เครื่องมือประเมินการเข้าถึงเว็บไซต์แบบกึ่งอัตโนมัติ (Semi-automated) ที่พัฒนาตามข้อกำหนดในบทที่ 1–3
ของรายงานโครงงาน ครอบคลุมกฎย่อยสี่กฎภายใต้หลักเกณฑ์ WCAG 2.1 สามข้อ คือ SC 1.1.1, SC 1.3.1 และ SC 1.4.3

## การเริ่มใช้งาน

ระบบเป็นไฟล์แบบเปิดใช้งานได้ทันที ไม่ต้องติดตั้งไลบรารีหรือคอมไพล์ใด ๆ

| ต้องการทำอะไร | วิธีเปิด |
| --- | --- |
| ใช้เครื่องมือประเมิน | เปิด `index.html` ด้วยเบราว์เซอร์ |
| ดูผลการวัดความแม่นยำของระบบ | เปิด `tests/runner.html` ด้วยเบราว์เซอร์ |

โหมดวาง HTML และการรันชุดทดสอบใช้งานได้จากไฟล์โดยตรง (`file://`)
ส่วน**โหมดระบุลิงก์**ต้องเปิดผ่านเว็บเซิร์ฟเวอร์ เพราะเบราว์เซอร์ปิดกั้นคำขอข้ามต้นทางจากไฟล์ในเครื่อง

```bash
npx http-server -p 8080 .    # แล้วเปิด http://localhost:8080/index.html
```

## กฎตรวจที่ระบบใช้

ทุกกฎพัฒนาตามตารางกฎตรวจในบทที่ 2.5 แบบหนึ่งต่อหนึ่ง

| รหัสกฎ | หลักเกณฑ์ | เงื่อนไขไม่ผ่าน | ระดับ |
| --- | --- | --- | --- |
| `R-ALT-01` | SC 1.1.1 | `<img>` ไม่มีแอตทริบิวต์ `alt` เลย | วิกฤต |
| `R-ALT-02` | SC 1.1.1 | `alt` เป็นค่าว่าง — ให้สถานะ *ต้องตรวจเพิ่ม* เพราะถูกต้องเฉพาะกรณีภาพตกแต่ง | แนะนำ |
| `R-HEAD-01` | SC 1.3.1 | ระดับหัวข้อกระโดดข้ามมากกว่าหนึ่งระดับจากหัวข้อก่อนหน้า | ควรแก้ |
| `R-LABEL-01` | SC 1.3.1 | ช่องกรอกไม่มี `<label for>`, `<label>` ครอบ, `aria-label` หรือ `aria-labelledby` | วิกฤต |
| `R-CONTRAST-01` | SC 1.4.3 | อัตราส่วนความคมชัดต่ำกว่า 4.5 ต่อ 1 | ควรแก้ |

ข้อยกเว้นที่ระบบข้ามการตรวจ: `role="presentation"` และ `aria-hidden="true"` สำหรับภาพ,
`type` เท่ากับ `hidden`, `submit`, `button`, `reset`, `image` สำหรับช่องกรอก,
และองค์ประกอบที่กำหนดสีเพียงด้านเดียวสำหรับความคมชัด
ข้อความใน `placeholder` ไม่นับเป็นป้ายกำกับที่ถูกต้อง

## การคำนวณคะแนน

หน่วยนับพื้นฐานคือคู่ "องค์ประกอบ–กฎตรวจ" ซึ่งมีสถานะได้สี่แบบตามบทที่ 3.6.1
เฉพาะสถานะ *ผ่าน* และ *ไม่ผ่าน* เท่านั้นที่นับในตัวหาร

```
FailureRate(i) = จำนวนคู่ "ไม่ผ่าน" ของหลักเกณฑ์ i / จำนวนคู่ "ผ่าน" + "ไม่ผ่าน" ของหลักเกณฑ์ i
PreliminaryScore = 100 × [ 1 − ( Σ wᵢ × FailureRate(i) ) / Σ wᵢ ]
```

น้ำหนัก `w` เท่ากับ 3 : 2 : 2 สำหรับ SC 1.1.1 : SC 1.3.1 : SC 1.4.3
เมื่อหลักเกณฑ์ใดไม่มีคู่ที่นับได้เลย ระบบกำหนด `FailureRate` เป็นศูนย์ จึงไม่หักคะแนนในหลักเกณฑ์นั้น
และแจ้งเตือนผู้ใช้ไว้ที่หน้าผลการประเมินเสมอว่าคะแนนส่วนนั้นไม่ได้มาจากการตรวจจริง

**การรวมคำตอบจากแบบประเมิน Checklist** — บทที่ 3.6.1 กำหนดว่าคู่สถานะ *ต้องตรวจเพิ่ม*
ต้องรอคำตอบจาก Checklist และถูกตัดออกจากทั้งตัวเศษและตัวหารหากผู้ใช้ไม่ตอบ ระบบจึงนำไปพัฒนาต่อดังนี้

- คำถามหนึ่งข้อต่อหนึ่งหลักเกณฑ์ เมื่อผู้ใช้ตอบจะเพิ่มคู่ตรวจของมนุษย์หนึ่งคู่ (ตอบ *ใช่* เป็นผ่าน, ตอบ *ไม่ใช่* เป็นไม่ผ่าน)
- คำตอบของหลักเกณฑ์ใดจะเปลี่ยนสถานะคู่ *ต้องตรวจเพิ่ม* ของหลักเกณฑ์นั้นทั้งหมดไปตามคำตอบด้วย
- หากเลือก *ยังไม่ได้ตรวจ* จะไม่เพิ่มคู่ใด และคู่ *ต้องตรวจเพิ่ม* ยังคงถูกตัดออกจากการคำนวณ

## ผลการวัดความแม่นยำ

| หลักเกณฑ์ | TP | FP | FN | TN | Precision | Recall | F1-score |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| SC 1.1.1 | 16 | 0 | 0 | 27 | 1.000 | 1.000 | 1.000 |
| SC 1.3.1 | 31 | 0 | 0 | 86 | 1.000 | 1.000 | 1.000 |
| SC 1.4.3 | 26 | 0 | 0 | 53 | 1.000 | 1.000 | 1.000 |

**การตรวจสอบอื่นที่ผ่านทั้งหมด**

- สูตรคะแนนให้ผล 57.62 ตรงกับตัวอย่างการคำนวณทีละขั้นในบทที่ 3.7.2
- กรณีตัวหารเป็นศูนย์ให้คะแนน 100.00 ตามที่กำหนดไว้
- มาตรการความปลอดภัยของลิงก์ผ่านครบทั้ง 16 กรณีทดสอบ (ปฏิเสธ 13 กรณี อนุญาต 3 กรณี)

### วิธีอ่านค่า F1-score เท่ากับ 1.000 อย่างถูกต้อง

ค่านี้หมายความว่า **โปรแกรมทำงานตรงตามข้อกำหนดในตารางกฎตรวจของบทที่ 2.5 ทุกกรณีในชุดทดสอบ**
ไม่ได้หมายความว่าเครื่องมือตรวจพบปัญหาการเข้าถึงในเว็บไซต์จริงได้ครบถ้วน เหตุผลคือ

1. ค่าอ้างอิงในชุดทดสอบกำหนดขึ้นจากเงื่อนไขผ่าน/ไม่ผ่านในบทที่ 2.5 ซึ่งเป็นข้อกำหนดชุดเดียวกับที่ใช้เขียนโปรแกรม
   การได้ค่าสูงจึงยืนยัน "ความถูกต้องของการนำข้อกำหนดไปพัฒนา" (Implementation Correctness) เป็นหลัก
2. กฎที่ตรวจเป็นกฎเชิงโครงสร้างที่มีเงื่อนไขชัดเจนและไม่มีความกำกวม จึงคาดหวังค่าสูงได้ตั้งแต่ต้น
3. ยังไม่ได้ทดสอบกับเว็บไซต์จริงในเชิงปริมาณ เพราะไม่ทราบจำนวนข้อบกพร่องที่แท้จริงล่วงหน้า
   ตามที่ระบุไว้ในวัตถุประสงค์ข้อสุดท้ายของบทที่ 1.2

การอ้างว่าเครื่องมือ "พร้อมใช้งานจริง" จากตัวเลขนี้เพียงอย่างเดียวจึงเป็นการกล่าวอ้างเกินขอบเขตของหลักฐาน
ตามที่บทที่ 3.7.3 ระบุไว้

## ข้อจำกัดที่ทราบ

**ข้อจำกัดจากการไม่ใช้เบราว์เซอร์เสมือน (บทที่ 3.3.4)** — ระบบใช้ `DOMParser` ซึ่งไม่จำลองการแสดงผลจริง จึงตรวจไม่ได้ในกรณีต่อไปนี้

| ตรวจไม่ได้ | ผลกระทบต่อคะแนน |
| --- | --- |
| เนื้อหาที่ JavaScript สร้างขึ้นภายหลัง | ไม่ถูกนับเป็นจุดตรวจเลย ทั้งด้านบวกและด้านลบ |
| สีจากไฟล์ CSS ภายนอก | จุดตรวจ SC 1.4.3 อาจน้อยกว่าความเป็นจริงมาก ทำให้น้ำหนักด้านนี้ต่ำกว่าที่ตั้งใจ |
| สีที่สืบทอดจากองค์ประกอบแม่ | องค์ประกอบลูกที่ไม่ประกาศสีซ้ำถูกข้ามการตรวจ |
| ความโปร่งใส (alpha) ของสี | อัตราส่วนที่คำนวณอาจคลาดเคลื่อนจากค่าที่ตาเห็นจริง ระบบแจ้งเตือนไว้ในผลรายจุด |

**ข้อจำกัดอื่นของรุ่นปัจจุบัน**

- ใช้เกณฑ์ 4.5 ต่อ 1 กับทุกกรณี ไม่แยกใช้เกณฑ์ผ่อนปรน 3 ต่อ 1 สำหรับข้อความขนาดใหญ่
  เพราะไม่ทราบขนาดตัวอักษรจริงหลังการจัดรูปแบบ เป็นการเลือกทางที่ปลอดภัยไว้ก่อน
- กฎ `R-ALT-01` ยึดตามข้อยกเว้นที่ระบุไว้ในบทที่ 2.5 อย่างเคร่งครัด จึงรับเฉพาะ `role="presentation"`
  ยังไม่รับ `role="none"` ซึ่งมีความหมายเทียบเท่ากันตามข้อกำหนด ARIA
- การตรวจความปลอดภัยของลิงก์ทำงานฝั่งผู้ใช้ก่อนส่งคำขอ และครอบคลุมเฉพาะรูปแบบที่อยู่ที่ระบุไว้ในบทที่ 3.3.2
  ไม่ได้ป้องกันการเปลี่ยนเส้นทาง (Redirect) ไปยังที่อยู่ภายในหลังส่งคำขอไปแล้ว
  และไม่สรุปว่าระบบปลอดภัยจากการโจมตีทุกรูปแบบ
- ยังไม่มีการแยกบัญชีผู้ใช้ (Multi-tenant) แผ่นงานประวัติเป็นทรัพยากรส่วนตัวของผู้ดูแลระบบเท่านั้น
- บริการตัวกลางที่ใช้ในโหมดระบุลิงก์เป็นบริการสาธารณะของบุคคลที่สาม ความพร้อมใช้งานจึงอยู่นอกเหนือการควบคุม
  ระบบลองเรียงตามลำดับสามช่องทาง และแนะนำให้เปลี่ยนไปใช้โหมดวางโค้ดเองเมื่อทุกช่องทางล้มเหลว

## การติดตั้งระบบหลังบ้าน

ดูขั้นตอนโดยละเอียดในหัวข้อคำอธิบายส่วนหัวของไฟล์ `apps-script/Code.gs` โดยสรุปคือ
สร้าง Google Sheets ใหม่ เปิด Apps Script วางโค้ดจากไฟล์ดังกล่าว แล้ว Deploy เป็น Web app
โดยตั้งค่า Execute as เป็นบัญชีผู้ดูแลระบบ และ Who has access เป็น Anyone
จากนั้นนำลิงก์ที่ลงท้ายด้วย `/exec` ไปวางในช่อง "ที่อยู่ Web App" ของหน้าเว็บ

ระบบส่งเฉพาะค่าสรุปเชิงตัวเลขไปบันทึก ได้แก่ วันเวลา เว็บไซต์ที่ตรวจ คะแนน จำนวนจุดที่ต้องแก้
และอัตราไม่ผ่านแยกตามหลักเกณฑ์ **ไม่ส่งและไม่จัดเก็บโค้ด HTML ต้นฉบับ** ตามบทที่ 3.3.3
ฝั่ง Apps Script ปฏิเสธคำขอที่แนบโค้ดต้นฉบับมาด้วยอีกชั้นหนึ่ง

## การรันชุดทดสอบแบบอัตโนมัติ

`tests/runner.html` เปิดผลลัพธ์ไว้ที่ `window.__RESULTS__` และตั้งค่า `data-testrun` บนแท็ก `<html>`
เมื่อรันเสร็จ จึงนำไปรันในระบบทดสอบอัตโนมัติได้

```js
await page.goto('http://localhost:8080/tests/runner.html');
await page.waitForSelector('html[data-testrun]');
const results = await page.evaluate(() => window.__RESULTS__);
console.assert(results.overallOk, 'มีเกณฑ์การตรวจรับที่ยังไม่ผ่าน');
```
