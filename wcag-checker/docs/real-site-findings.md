# ผลการสาธิตการใช้งานกับเว็บไซต์จริง

เอกสารนี้บันทึกผลการทดสอบเครื่องมือกับหน้าเว็บของเว็บไซต์จริงที่ให้บริการอยู่จริง
ตามวัตถุประสงค์ข้อสุดท้ายในบทที่ 1.2 และขอบเขตในบทที่ 3.4.2 ซึ่งระบุว่าการทดสอบกับเว็บไซต์จริง
ใช้เพื่อ **สาธิตและประเมินความทนทานเชิงคุณภาพเท่านั้น** ไม่ใช้คำนวณ Precision, Recall หรือ F1-score
เนื่องจากไม่ทราบจำนวนข้อบกพร่องที่แท้จริงล่วงหน้า

## ข้อจำกัดสำคัญของการทดสอบชุดนี้

สภาพแวดล้อมที่ใช้รันการทดสอบมีนโยบายเครือข่ายที่ปิดกั้นการเชื่อมต่อออกสู่อินเทอร์เน็ตเกือบทั้งหมด
(เกตเวย์ตอบรหัส 403 ที่ขั้นตอน CONNECT) เว็บไซต์ที่เข้าถึงได้จึงมีเพียง `pypi.org` แห่งเดียว
ผลในเอกสารนี้จึงเป็นการสาธิตกับเว็บไซต์เดียวและไม่ครอบคลุมความหลากหลายของเว็บไซต์จริง

**สิ่งที่ยังต้องดำเนินการเพิ่ม** คือทดสอบกับเว็บไซต์ในบริบทที่โครงงานกำหนดเป็นกลุ่มเป้าหมาย
โดยเฉพาะเว็บไซต์หน่วยงานภาครัฐไทยตามบทที่ 3.2.2 ซึ่งต้องรันบนเครื่องที่เชื่อมต่ออินเทอร์เน็ตได้ตามปกติ

## วิธีดำเนินการ

ดึง HTML ต้นฉบับของหน้าเว็บด้วยคำสั่ง `curl` แล้วนำเข้าสู่โมดูลวิเคราะห์ชุดเดียวกับที่ระบบใช้
ผ่านโหมดวางโค้ด ซึ่งใช้ตรรกะเดียวกับโหมดระบุลิงก์ทุกประการหลังได้รับ HTML แล้ว (ตามบทที่ 1.1.1)
ไม่ตอบแบบประเมิน Checklist ในการทดสอบนี้ เพื่อให้เห็นผลจากการตรวจอัตโนมัติล้วน ๆ

## ข้อค้นพบ

### 1. ระบบทำงานได้ต่อเนื่องกับ HTML จริงทุกหน้า

หน้าที่ทดสอบมีขนาดตั้งแต่ 294 ถึง 959 องค์ประกอบ ระบบวิเคราะห์ได้ครบทุกหน้าโดยไม่หยุดทำงาน
ไม่เกิดข้อผิดพลาดของโปรแกรม และใช้เวลาต่ำกว่าสิบมิลลิวินาทีทุกหน้า ยืนยันความทนทานในระดับที่
ตั้งเป้าไว้ ซึ่งสอดคล้องกับผลจากชุดทดสอบ I ที่ออกแบบมาเพื่อทดสอบโค้ดผิดรูปโดยเฉพาะ

### 2. คะแนนเต็ม 100.00 ทุกหน้า แต่ไม่ได้แปลว่าเว็บไซต์ไม่มีปัญหา

นี่คือข้อค้นพบที่สำคัญที่สุดของการทดสอบชุดนี้ และเป็นหลักฐานเชิงประจักษ์ที่ยืนยันความจำเป็น
ของข้อกำหนดในบทที่ 3.7.2 ที่บังคับให้แสดงจำนวนจุดที่ตรวจได้ควบคู่กับคะแนนเสมอ

- **SC 1.4.3 ตรวจได้ศูนย์จุดในทุกหน้า** ตรวจสอบด้วยมือแล้วพบว่าหน้าเหล่านี้ไม่มีแอตทริบิวต์ `style`
  แม้แต่ตัวเดียว การจัดรูปแบบทั้งหมดอยู่ในไฟล์ CSS ภายนอกสี่ไฟล์ ระบบจึงไม่มีข้อมูลสีให้คำนวณเลย
  ตามกฎในบทที่ 3.7.2 อัตราไม่ผ่านของหลักเกณฑ์นี้ถูกกำหนดเป็นศูนย์ จึงไม่หักคะแนน
  ทั้งที่ **ไม่ได้ตรวจอะไรเลย** ตรงกับข้อจำกัดที่ระบุไว้ในตารางบทที่ 3.3.4 แถวที่สอง
- **SC 1.1.1 ตรวจได้เพียง 1 จุดจาก 15–16 จุด** ภาพเกือบทั้งหมดในหน้าเหล่านี้ตั้ง `alt` เป็นค่าว่าง
  ซึ่งระบบให้สถานะ *ต้องตรวจเพิ่ม* ไม่ใช่ผ่าน จึงไม่ถูกนับในตัวหาร
- มีเพียง **SC 1.3.1 เท่านั้นที่มีความครอบคลุมในระดับที่มีความหมาย** (5–76 จุดต่อหน้า)

คะแนน 100.00 ที่แสดงจึงมาจากการตรวจได้จริงเพียง 6 ถึง 92 คู่จากองค์ประกอบทั้งหน้า
หากผู้ใช้อ่านเฉพาะตัวเลขคะแนนโดยไม่ดูคอลัมน์ความครอบคลุม จะเข้าใจผิดว่าเว็บไซต์ผ่านการประเมิน
อย่างสมบูรณ์ ข้อความเตือนที่ระบบแสดงเมื่อพบหลักเกณฑ์ที่ตรวจได้ศูนย์จุดจึงทำงานตามที่ออกแบบไว้
และมีความจำเป็นจริงในการใช้งานกับเว็บไซต์จริง

### 3. สัดส่วนภาพที่ใช้ `alt` ค่าว่างในเว็บไซต์จริงสูงมาก

หน้าแรกมีภาพ 16 ภาพ โดย 15 ภาพตั้ง `alt=""` และมีเพียงภาพเดียวที่มีข้อความบรรยาย (`alt="PyPI"`)
สัดส่วนนี้ยืนยันว่าการออกแบบให้กฎ `R-ALT-02` คืนสถานะ *ต้องตรวจเพิ่ม* แทนที่จะตัดสินว่าผ่านหรือไม่ผ่าน
เป็นทางเลือกที่ถูกต้อง เพราะระบบแยกไม่ได้ว่าภาพเหล่านั้นเป็นภาพตกแต่งจริงหรือเป็นภาพที่สื่อความหมาย
แต่ผู้พัฒนาลืมใส่คำบรรยาย ในทางกลับกันก็หมายความว่า **คำตอบของผู้ประเมินในแบบประเมิน Checklist
มีน้ำหนักต่อคะแนนสุดท้ายมากกว่าที่คาดไว้** เมื่อใช้กับเว็บไซต์จริง

### 4. พบกรณีที่บริการตัวกลางเข้าถึงไม่ได้จริงตามที่บทที่ 1.1.1 ระบุไว้

จากหกหน้าที่พยายามดึง มีสองหน้า (`/project/requests/` และ `/search/?q=accessibility`)
ที่เซิร์ฟเวอร์ตอบกลับเป็นหน้าตรวจสอบบอท (`Client Challenge`) ขนาด 3,038 ไบต์ แทนเนื้อหาจริง
ตรงกับข้อจำกัดที่ระบุไว้ในตารางโหมดรับข้อมูลของบทที่ 1.1.1 ว่าเว็บไซต์ที่ปิดกั้นด้วย CAPTCHA
หรือ Firewall จะดึงเนื้อหาไม่ได้ กรณีนี้ระบบไม่ได้แจ้งเตือนว่าเนื้อหาที่ได้ไม่ใช่หน้าจริง
เพราะได้รับ HTML ที่ถูกต้องตามรูปแบบกลับมา จึงวิเคราะห์ตามปกติและให้ผลที่ไม่มีความหมาย

**ข้อเสนอแนะสำหรับการพัฒนาต่อ:** ควรเพิ่มการตรวจจับเบื้องต้นว่าเนื้อหาที่ดึงมาน่าจะเป็นหน้า
ตรวจสอบบอทหรือหน้าแสดงข้อผิดพลาดหรือไม่ เช่น ดูจากขนาดที่เล็กผิดปกติหรือคำสำคัญในชื่อเรื่อง
แล้วแจ้งเตือนผู้ใช้ก่อนแสดงคะแนน

### 5. การตรวจสอบความถูกต้องของผลด้วยมือ

ตรวจสอบผลของทั้งสี่หน้าเทียบกับการนับจาก DOM โดยตรง พบว่าจำนวนคู่ตรวจแต่ละสถานะตรงกันทุกค่า
เช่น หน้าแรกนับได้ภาพ 16 ภาพ (มีข้อความบรรยาย 1, ค่าว่าง 15) หัวข้อเรียงเป็น h1 h2 h2 h2 h2
(หัวข้อแรกไม่ตรวจ อีกสี่หัวข้อผ่าน) และช่องกรอกหนึ่งช่องที่มี `label` ผูกด้วยแอตทริบิวต์ `for`
ซึ่งตรงกับที่ระบบรายงานคือ SC 1.1.1 ตรวจได้ 1 จาก 16 และ SC 1.3.1 ตรวจได้ 5 จาก 6 ทุกประการ
ไม่พบการแจ้งเตือนผิดพลาด (False Positive) ในหน้าใดเลย

## สรุป

การสาธิตกับเว็บไซต์จริงยืนยันสองประเด็น ประการแรกคือระบบทำงานได้อย่างทนทานกับ HTML จริง
ที่มีขนาดใหญ่และซับซ้อนกว่าชุดทดสอบที่ผู้วิจัยพัฒนา และให้ผลที่ถูกต้องเมื่อตรวจสอบย้อนกลับด้วยมือ
ประการที่สองซึ่งสำคัญกว่าคือ **ข้อจำกัดด้านความครอบคลุมของเครื่องมือปรากฏชัดเจนกว่ามากเมื่อใช้กับ
เว็บไซต์จริง** เมื่อเทียบกับชุดทดสอบที่ออกแบบมาให้มีจุดตรวจครบทุกหลักเกณฑ์
เว็บไซต์ที่พัฒนาตามแนวปฏิบัติสมัยใหม่จะแยกการจัดรูปแบบไปไว้ในไฟล์ CSS ทั้งหมด
ทำให้หลักเกณฑ์ SC 1.4.3 ไม่มีจุดตรวจเลยในทางปฏิบัติ

ข้อค้นพบนี้ไม่ได้ลดคุณค่าของเครื่องมือ แต่กำหนดขอบเขตการใช้งานที่เหมาะสมให้ชัดขึ้น คือเหมาะกับ
การตรวจโค้ดส่วนที่ผู้พัฒนากำลังเขียนอยู่ซึ่งมักมี style กำกับไว้โดยตรง มากกว่าการตรวจหน้าเว็บ
ที่เผยแพร่แล้วทั้งหน้า และย้ำว่าการอ่านคะแนนโดยไม่ดูความครอบคลุมควบคู่กันเป็นการตีความที่ผิด
